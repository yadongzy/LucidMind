# 第十一条：测试铁律（补充第四条）

```
测试是项目质量的证据，不是形式。以下规则不可违反：

1. 回归测试（防退化）
   - 每次代码修改后，必须运行: python -m pytest tests/test_brain.py -v
   - 新增功能必须新增对应测试用例
   - 已有测试用例数量只能增加，不能减少
   - 测试通过数下降 = 退化 = 立即修复

2. 测试不可删除/弱化
   - 禁止删除任何已通过的测试用例
   - 禁止将 assert 改为 pass 或注释掉
   - 禁止降低测试标准（如把 > 100 改为 > 10）
   - 如需修改测试，必须说明原因并保证新测试更严格

3. 测试覆盖要求
   - 每个 Port 接口: ≥ 2 个测试（正向 + 异常）
   - 每个 Adapter: ≥ 1 个集成测试
   - brain.py 核心方法: 每个公开方法 ≥ 1 个测试
   - 新增工具: 必须有工具调用成功 + 失败的测试

4. 浏览器测试标准（强化第四条）
   - **铁律: 用户可见功能必须通过真实浏览器操作验证，无例外**
   - 用户可见功能 = 对话、思维流、工具调用结果、会话管理、UI交互
   - 内部模块（memory_curator、json_lessons逻辑、向量检索）用 pytest 单元测试验证
   - 后端 API 功能如果有前端入口，必须验证前端可见性
   - HTTP API 测试（requests/curl）可用于验证接口正确性，但不替代浏览器测试

   **真实浏览器测试的正确方法：**
   - 通过 WebSocket (ws://localhost:8765/ws) 发送消息到大脑对话框
   - 用户在浏览器中实时监控全流程（思维流→工具调用→回复）
   - 使用 scripts/browser_test.py 脚本执行，脚本通过WebSocket发送并监听事件
   - 禁止用 HTTP POST /api/chat 替代（那不是浏览器测试，用户看不到全流程）
   - 测试消息会出现在用户的浏览器对话框中，用户能看到完整的思维流和回复
   - 格式: 输入 → 思维流(元认知🧠) → 回复 → 耗时 → 判定
   - 流式输出: 长回复必须验证 .streaming 元素出现
   - 元认知: 验证 thinking-box 中包含 🧠 前缀的计划
   - 记忆: 跨轮次验证（记住 → 干扰 → 回忆）

5. 测试命令基准
   | 场景 | 命令 |
   |------|------|
   | 单元测试 | python -m pytest tests/test_brain.py -v |
   | 全量测试 | python -m pytest tests/ -v --tb=short |
   | 浏览器测试 | python tests/test_final_s17.py |
   | 流式测试 | python tests/test_streaming.py |
   | 元认知测试 | python tests/test_metacog_stream.py |

6. 测试结果记录
   - 所有测试结果必须记录在 PROGRESS.md
   - 格式: 测试名 | 通过数/总数 | 日期 | 关键发现
   - 禁止只写"通过"不写具体数据
```
