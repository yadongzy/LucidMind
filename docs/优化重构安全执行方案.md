# LucidMind 优化重构安全执行方案

> 文档版本：v1.0  
> 编制日期：2026-09-07  
> 适用范围：LucidMind 核心大脑、任务执行、队列、记忆、工具调用、恢复机制、API 与测试体系  
> 核心原则：行为保持、风险前置、分批交付、全程可观测、随时可停止、每步可验证、每批可回滚

## 1. 文档目的

本方案用于指导 LucidMind 在不中断既有能力、不损坏持久化数据、不放大安全边界的前提下完成系统优化与架构重构。方案重点解决以下问题：

1. 核心模块职责交叉，长期演进可能增加理解、修改和测试成本。
2. 长任务涉及队列、分解、重试、超时、状态持久化和历史压缩，局部修改容易产生跨模块副作用。
3. 当前目录不是 Git 仓库，缺少标准化版本基线和低成本代码回滚能力，应在任何实质性重构前优先补齐。
4. 数据目录包含会话、记忆、任务队列、嵌入缓存和诊断记录，必须将代码回滚与数据回滚分开设计。
5. 已有安全测试、重试、健康检查和历史压缩能力需要保留，并逐步统一成明确的安全控制面。

本文是执行基线，不直接授权一次性大改。每个阶段都必须满足进入条件、验证条件和退出条件。

## 2. 当前系统观察与重构焦点

根据当前工程结构，优先关注以下能力边界：

- 任务编排与执行：任务分解、命令队列、任务执行器、目标跟踪。
- 可靠性：LLM 与工具重试、超时、失败分类、自检、降级和教师升级。
- 上下文与记忆：会话记录、历史压缩、压缩前记忆刷新、摘要与持久化。
- 工具安全：工具作用域、危险操作拦截、插件路径校验、网络与文件访问边界。
- API 边界：请求入口、流式响应、异常映射、取消和服务关闭。
- 数据资产：任务队列、会话、记忆、缓存、配置、诊断日志及备份文件。

建议将目标架构收敛为五个相互隔离的层次：

1. **入口层**：HTTP、WebSocket、CLI 和后台守护进程，只负责协议转换与身份上下文。
2. **应用层**：目标、任务、会话等用例编排，不直接实现底层存储或外部工具细节。
3. **领域层**：任务状态机、重试判断、风险决策、完成条件等纯业务规则。
4. **端口与适配层**：LLM、记忆、工具、流、持久化等接口及实现。
5. **基础设施层**：文件、数据库、网络、进程、日志、指标与备份。

依赖方向必须由外向内，领域规则不得反向依赖 API、具体数据库或具体模型供应商。

## 3. 重构目标与可量化完成标准

### 3.1 功能目标

- 既有公开 API、主要 CLI 行为、任务生命周期与数据格式默认保持兼容。
- 长任务支持明确的任务状态、心跳、检查点、取消、暂停、恢复和失败原因。
- 重试只针对可重试故障，永久错误、权限错误和数据校验错误不得盲目重试。
- 核心数据写入具备原子性，进程崩溃后能够检测并恢复到最后有效状态。
- 新旧实现能够通过特性开关并存，在灰度期间可以快速切回旧实现。

### 3.2 质量门槛

- 全量自动化测试通过，新增或变更模块具备单元、契约及关键路径集成测试。
- 关键行为的回归用例覆盖成功、超时、取消、进程中断、重复请求、部分写入和恢复。
- 静态检查、依赖安全检查、密钥扫描和配置校验全部通过。
- 性能基准无非预期退化。关键路径 P95 延迟建议不劣化超过 10%，吞吐不下降超过 10%，内存峰值不增长超过 15%。
- 灰度观察期无数据损坏、无不可恢复任务、无高严重度安全事件。

### 3.3 明确不在本轮范围内的事项

- 不同时更换主要 LLM 供应商、存储引擎和客户端协议。
- 不在同一批次中进行大规模功能开发与架构重构。
- 不以删除旧实现来证明重构完成，旧实现应在稳定观察期结束后单独清理。
- 不使用生产数据直接进行破坏性迁移试验。

## 4. 安全治理机制

### 4.1 最小权限与隔离

- 开发和自动化默认只能写入项目工作区及专用临时目录。
- 默认关闭网络，仅对必需域名按白名单开放，并记录外联目的和数据类型。
- 生产凭据不得进入源码、提示词、日志、补丁或测试快照。
- 开发、测试、预发布和生产使用隔离的配置、凭据、数据目录与服务账号。
- 高风险操作，包括删除、覆盖、批量迁移、外部写入和权限提升，必须有显式审批点。

### 4.2 变更保护

- 在开始重构前初始化 Git，创建受保护的主分支和重构分支。
- 禁止直接向主分支推送，合并必须经过测试、审查和回滚检查。
- 建立 CODEOWNERS 或等效责任机制，核心执行、安全、数据迁移模块至少需要双人审查。
- 每个提交只完成一个可描述、可验证的小步骤，提交后系统保持可运行。
- 禁止将格式化全库、依赖升级和业务改动混入同一提交。

### 4.3 数据安全

- 所有持久化文件写入采用临时文件、刷新落盘、原子重命名的方式。
- 对 JSON、JSONL、SQLite 和缓存文件定义版本、校验规则和损坏检测。
- 迁移前执行只读盘点、备份、恢复演练和容量检查。
- 迁移脚本必须具备 dry-run、幂等、进度记录、校验和及可重入能力。
- 日志默认脱敏，禁止记录访问令牌、完整个人数据、原始认证头和敏感提示内容。

### 4.4 长任务安全

- 每个任务使用稳定 task_id、attempt_id 和 idempotency_key。
- 明确状态机：queued、running、paused、succeeded、failed、cancelled、recovery_required。
- 状态转移必须校验，禁止已完成任务重新进入 running，除非创建新 attempt。
- 每个长任务定期写检查点，检查点包含输入摘要、当前阶段、已完成副作用和下一步。
- 设置任务总时限、单步骤时限、无进展时限与重试预算。
- 取消采用协作式取消，在安全点停止，并执行已登记的补偿动作。
- 对外部副作用使用 outbox、幂等键或去重表，避免恢复后重复执行。

## 5. 回滚与恢复设计

### 5.1 四层回滚模型

1. **代码回滚**：通过小提交、标签和 revert 回退实现，不依赖覆盖文件。
2. **配置回滚**：配置版本化，保留上一稳定版本，启动失败时自动回退。
3. **数据回滚**：使用快照、备份、迁移反向脚本或兼容读取恢复。
4. **流量回滚**：通过特性开关、灰度比例或双实现路由即时切换。

代码回滚不能替代数据回滚。若新版本已经写入不兼容数据，仅回退代码可能导致二次故障，因此数据格式变更应采用扩展与收缩模式：先兼容读、再双写或新写、完成回填，最后才移除旧格式。

### 5.2 必备恢复资产

- 重构前基线标签、依赖锁定信息和运行环境清单。
- 数据目录完整备份及 SHA-256 清单。
- 数据恢复脚本与逐项校验脚本。
- 配置快照、数据库 schema 版本和迁移日志。
- 运行手册，包含故障判定、停止服务、恢复、验证和重新放量步骤。
- 紧急联系人、决策人、回滚执行人和沟通渠道。

### 5.3 自动回滚触发条件

满足任意条件应停止放量，并按预案回滚：

- 发现数据丢失、不可解析、重复副作用或无法恢复的任务。
- 错误率或超时率显著超过基线并持续两个观察窗口。
- P95 延迟、内存、CPU 或队列积压超过预设红线。
- 健康检查连续失败，或安全审计产生高严重度告警。
- 用户关键路径出现大面积失败或结果语义明显偏移。

### 5.4 紧急回滚步骤

1. 冻结部署和迁移，停止新的写入任务进入受影响实现。
2. 将流量开关切回最后稳定实现，保留故障现场和日志。
3. 等待在途任务到达安全点。无法安全完成的任务标记为 recovery_required。
4. 恢复稳定配置和代码版本。
5. 如发生数据变化，先隔离损坏数据，再按恢复脚本恢复备份并重放合法增量。
6. 执行冒烟测试、数据校验、队列一致性检查和关键用户路径验证。
7. 记录时间线、影响范围、恢复证据和遗留任务，未经复盘不得直接再次放量。

## 6. 分阶段执行计划

### 阶段 0：建立基线与可回退环境

**任务**

- 初始化 Git 仓库，排除凭据、缓存、数据库日志、运行日志、截图和生成物。
- 对当前可运行状态建立基线提交和标签。
- 固化 Python 版本、依赖版本、启动方式、环境变量和外部服务清单。
- 备份 data 及关键配置，生成文件校验清单并完成一次异地恢复演练。
- 运行现有测试，记录通过率、耗时、失败项、CPU、内存和响应延迟。
- 编写最小冒烟测试，覆盖启动、健康检查、普通对话、工具调用、长任务和关闭。

**退出条件**

- 可以从零恢复代码和数据，并通过冒烟测试。
- 基线缺陷已记录，不把历史失败误归因于重构。

### 阶段 1：特征化测试与接口冻结

**任务**

- 为任务分解、队列调度、执行器、重试、压缩、记忆刷新和 API 边界增加特征化测试。
- 记录当前输入输出、异常类型、状态变化和持久化格式。
- 为 LLM、工具、记忆、流和任务存储建立契约测试。
- 准备固定随机种子、假时钟、故障注入器和隔离的临时数据目录。

**退出条件**

- 高风险现有行为具有自动化保护网。
- 公开接口和明确允许改变的行为形成清单。

### 阶段 2：统一任务模型和状态机

**任务**

- 建立单一 Task、Attempt、Checkpoint 和 FailureReason 模型。
- 将散落的字符串状态收敛为显式状态机和受控转换函数。
- 区分业务失败、临时基础设施失败、权限失败、用户取消和系统中断。
- 引入幂等键、乐观版本号和任务租约，防止重复执行和并发覆盖。
- 保持旧数据读取兼容，并通过适配器逐步迁移调用方。

**退出条件**

- 状态机单元测试和并发测试通过。
- 新旧模型结果在影子比较中一致。

### 阶段 3：重构任务执行管线

**任务**

- 将准备、分解、排队、执行、验证、持久化和完成通知拆成可测试阶段。
- 将内联重试改为统一重试策略，加入指数退避、抖动和最大预算。
- 增加超时继承规则，子步骤时限不得突破父任务剩余时限。
- 增加取消令牌和安全点，确保取消不会留下半写数据。
- 对工具调用引入统一审计记录、风险等级、输入校验和结果大小限制。

**退出条件**

- 故障注入覆盖超时、限流、网络中断、工具异常、进程退出和重复投递。
- 所有失败均能映射为明确可操作的 FailureReason。

### 阶段 4：持久化与检查点加固

**任务**

- 为任务队列、会话、记忆和配置统一原子写入帮助模块。
- 为 JSONL 增加尾部损坏检测和安全截断策略，为 SQLite 定义事务与备份策略。
- 长任务在阶段边界写入检查点和副作用账本。
- 启动时扫描 running 状态的孤儿任务，根据租约和检查点决定恢复、失败或人工处理。
- 建立备份保留周期、恢复点目标 RPO 和恢复时间目标 RTO。

**建议初始目标**

- 关键任务状态 RPO 不超过 1 分钟。
- 本地单机服务 RTO 不超过 15 分钟。
- 关键数据至少保留每日快照和最近若干次部署前快照。

### 阶段 5：安全控制面与可观测性

**任务**

- 将工具安全检查、路径校验、网络策略和审批策略统一到一个可审计入口。
- 增加结构化日志与 correlation_id，串联请求、任务、attempt、工具调用和检查点。
- 建立指标：成功率、重试率、取消率、恢复率、队列深度、等待时间、执行时间和无进展时长。
- 建立健康检查、就绪检查和依赖降级状态。
- 为密钥泄漏、危险命令、数据迁移失败和异常外联增加告警。

### 阶段 6：灰度发布

**任务**

- 新实现默认关闭，通过特性开关按用户、任务类型或比例放量。
- 先执行影子读取或双计算，只比较结果，不产生双重外部副作用。
- 推荐按 1% → 10% → 25% → 50% → 100% 放量，每阶段至少跨越一个完整业务观察窗口。
- 每个阶段检查功能、性能、安全、数据一致性和回滚可用性。

**禁止事项**

- 未通过上一阶段门槛不得继续扩量。
- 不得在灰度期间删除旧实现或旧数据读取能力。

### 阶段 7：稳定化与旧代码清理

- 全量后保持至少 7 天稳定观察期。
- 关闭双写前做数据对账，关闭旧读前扫描未迁移数据。
- 删除旧实现、兼容开关和临时指标应作为独立提交。
- 更新架构图、接口文档、运行手册、故障演练和新成员指南。

## 7. 小提交建议

以下顺序要求每个提交都保持系统可运行：

1. 增加仓库忽略规则，不改变运行行为。
2. 固化基线测试命令和冒烟测试。
3. 增加统一任务状态枚举，旧字段继续兼容。
4. 增加状态转换校验，但先仅记录违规。
5. 将违规状态转换升级为测试失败和受控错误。
6. 增加 FailureReason 分类及旧异常适配。
7. 增加 Checkpoint 数据结构和只写不读路径。
8. 增加检查点恢复读取，但默认关闭。
9. 增加幂等键与重复任务检测。
10. 抽取统一原子文件写入模块并迁移一个低风险调用点。
11. 逐个迁移其余持久化调用点。
12. 抽取重试策略，先覆盖一个工具调用路径。
13. 迁移其余 LLM 和工具调用路径。
14. 增加取消令牌和安全点。
15. 增加孤儿任务探测，先仅报告。
16. 启用受控的孤儿任务恢复。
17. 增加新执行管线特性开关。
18. 影子运行并输出差异报告。
19. 小比例灰度新管线。
20. 全量后独立清理旧实现。

## 8. 测试矩阵

### 8.1 单元测试

- 状态机的合法和非法转换。
- 重试分类、退避、预算和截止时间。
- 幂等键、版本冲突、租约续期和取消。
- 数据序列化、版本迁移、尾部损坏和原子替换。

### 8.2 契约测试

- LLM、工具、记忆、流和任务存储端口。
- API 状态码、错误结构、事件顺序和兼容字段。
- 新旧任务模型互相读取的兼容性。

### 8.3 集成与恢复测试

- 执行中强制终止进程并重启。
- 检查点写入前、写入中和写入后故障。
- 外部工具已经成功但响应丢失时的去重。
- 磁盘满、权限不足、数据库锁、网络中断和限流。
- 取消与完成同时发生的竞态。

### 8.4 安全测试

- 路径遍历、命令注入、符号链接逃逸和未授权网络访问。
- 提示注入试图提升权限、读取工作区外文件或泄漏凭据。
- 插件和 MCP 输入边界、危险操作审批与审计日志。
- 日志、错误响应和诊断包中的敏感信息泄漏。

### 8.5 性能与长稳测试

- 不同队列深度和并发度下的延迟、吞吐和资源占用。
- 8 小时或更长持续运行，观察内存增长、任务泄漏和状态漂移。
- 大会话历史触发压缩后的信息保持与恢复能力。

## 9. 发布门禁与证据清单

每次灰度放量必须附带：

- 变更范围、风险等级、负责人和回滚负责人。
- 基线与本次测试结果。
- 数据格式变更及兼容证明。
- 备份位置、校验和、恢复演练记录。
- 特性开关名称和切换步骤。
- 监控面板、阈值和告警接收人。
- 回滚命令、健康验证命令和预计恢复时间。
- 已知限制及人工处理队列。

## 10. Codex 官方长任务规则与设置方法

以下内容依据截至 2026-09-07 可访问的 OpenAI 官方文档整理。

### 10.1 长任务提示词规则

官方建议长任务明确写出三类信息：

1. **Outcome**：最终要得到什么结果，而不只是“做某项活动”。
2. **Constraints**：必须遵守的工具、边界、兼容性和禁止事项。
3. **Verification**：可验证完成的测试、测量或审查标准。

相关工作应尽量留在同一个任务中，以便 Codex 延续上下文并判断完成条件。独立任务可以并行，但两个任务不应同时写同一份代码或同一连接数据源；并行代码工作应使用独立 Git worktree。

来源：https://learn.chatgpt.com/docs/long-running-work

### 10.2 Goal 模式

在 ChatGPT 桌面应用、Codex CLI 或 IDE 扩展中输入：

```text
/goal
```

目标文字同时作为首个提示和完成标准。若任务范围尚不清楚，先使用 `/plan` 梳理约束和可测量成功标准，再启动 `/goal`。运行过程中可在同一任务补充上下文、修改约束或要求状态摘要。

桌面应用可暂停、恢复、编辑或清除目标。预计断网前应先暂停，恢复连接后再继续。Goal 模式不会自动扩大权限，仍遵循既有沙箱和审批策略。

来源：https://learn.chatgpt.com/docs/long-running-work、[Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)

### 10.3 本地长任务建议设置

桌面应用执行本地长任务时，可在设置中启用 **Prevent sleep while running**，避免 Mac 在任务运行期间休眠；同时启用系统通知，以便任务需要输入或完成时及时获知。

推荐的安全基线是工作区可写、网络默认关闭、按需审批：

```toml
approval_policy = "on-request"
sandbox_mode = "workspace-write"
```

来源：https://learn.chatgpt.com/docs/long-running-work、[Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)、https://learn.chatgpt.com/docs/config-file/config-reference

### 10.4 上下文压缩与状态持久化

Codex 配置支持自动历史压缩阈值；不设置时使用模型默认值：

```toml
# 示例值需要依据所用模型上下文窗口和任务规模评估
model_auto_compact_token_limit = 80000
model_auto_compact_token_limit_scope = "total"
```

配置参考还说明 Codex 使用 SQLite 状态数据库保存 agent jobs 等可恢复运行状态。自定义压缩提示属于进阶设置，修改前应先验证压缩后是否仍保留目标、约束、当前阶段、未完成事项和关键决策。

来源：https://learn.chatgpt.com/docs/config-file/config-reference、https://learn.chatgpt.com/docs/long-running-work

### 10.5 CLI 非交互长任务

脚本或 CI 中使用 `codex exec`。默认是只读沙箱，需要改文件时显式设置工作区写权限：

```bash
codex exec --sandbox workspace-write \
  --json \
  -o refactor-result.md \
  "按 docs/优化重构安全执行方案.md 执行当前批准阶段；只修改批准范围；运行阶段测试；失败时停止并输出回滚说明。"
```

`--json` 会输出 JSONL 事件流，适合监控 thread、turn、命令、文件变化和错误；`-o` 将最终消息写入文件。需要稳定结构化结果时可使用 `--output-schema`。

远离可信隔离环境时不要使用：

```bash
codex exec --sandbox danger-full-access "..."
```

官方明确建议 danger-full-access 只用于受控环境，例如隔离的 CI runner 或容器。`--full-auto` 已属于弃用兼容参数，新脚本应显式使用沙箱设置。

来源：https://learn.chatgpt.com/docs/non-interactive-mode、[Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)

### 10.6 恢复非交互任务

两阶段流水线或中断后继续时，可恢复最近会话或指定会话：

```bash
codex exec resume --last "继续执行；先核对上次检查点和工作区差异，再开始下一步"

codex exec resume SESSION_ID "继续执行；不得重复已经完成的外部副作用"
```

Codex 默认要求在 Git 仓库内运行，以降低破坏性变更风险。`--skip-git-repo-check` 虽可绕过检查，但对于当前 LucidMind 不建议使用，应先完成 Git 基线建设。

来源：https://learn.chatgpt.com/docs/non-interactive-mode

### 10.7 Codex Cloud

需要后台运行、并行尝试或不想占用本地机器时，可使用 Codex Cloud：

- 连接 GitHub 或 GitLab。
- 为仓库创建隔离环境。
- 配置依赖、工具、环境变量和仅在确有必要时提供的 secrets。
- 启动任务后可观察日志或让任务在后台运行。
- 任务完成后先审查摘要和 diff，再决定继续修改或创建 PR。

Codex Cloud 的 setup 阶段可以联网安装指定依赖，agent 阶段默认离线；云环境 secrets 只在 setup 阶段可用，并在 agent 阶段前移除。需要 agent 联网时应显式配置，并优先使用域名白名单。

来源：https://learn.chatgpt.com/docs/cloud、[Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)

### 10.8 CI 中的凭据与权限分离

官方推荐 GitHub Actions 使用 `openai/codex-action`。不要把 API key 设置成会运行仓库代码的整个 job 的环境变量，因为构建脚本、测试和依赖钩子可能读取凭据。更安全的模式是：

1. Codex 任务只拥有仓库只读权限。
2. Codex 生成 patch artifact。
3. 独立 job 获取写权限，应用 patch 并创建 PR。
4. 有写权限的 job 不接收 OpenAI API key。

来源：https://learn.chatgpt.com/docs/non-interactive-mode

## 11. 推荐的 Codex 长任务模板

```text
/goal

Outcome:
完成 LucidMind 当前批准阶段的重构，使目标模块职责清晰，并保持现有外部行为兼容。

Constraints:
- 只修改本阶段批准范围。
- 不删除旧实现，使用特性开关接入新实现。
- 默认不访问工作区外文件，不开启非必要网络。
- 不修改或迁移生产数据，测试必须使用副本。
- 每个提交保持测试通过；遇到不可逆操作、数据格式冲突或高风险权限请求时暂停。
- 不覆盖用户已有的无关修改。

Verification:
- 运行本阶段单元、契约、集成和安全测试。
- 输出变更文件、测试结果、性能对比、数据兼容性检查和遗留风险。
- 演练特性开关回退，确认旧实现仍可运行。
- 未满足完成标准时不得宣称完成。
```

## 12. 执行前最终检查单

- [ ] 已初始化 Git 并建立稳定基线标签。
- [ ] 已确认敏感数据和运行生成物不进入版本库。
- [ ] 已备份关键数据并实际完成恢复演练。
- [ ] 已记录重构前功能和性能基线。
- [ ] 已明确本批次范围、非目标、负责人和回滚负责人。
- [ ] 已建立特性开关和回滚路径。
- [ ] 已为变更行为补足测试。
- [ ] 已设置指标、阈值和告警。
- [ ] 已确认新旧格式兼容策略。
- [ ] 已确认 Codex 的沙箱、网络和审批策略符合最小权限原则。
- [ ] 已把 Outcome、Constraints 和 Verification 写入长任务目标。
- [ ] 已安排发布后的观察窗口和复盘。

## 13. 结论

本轮重构的第一优先级不是移动代码，而是先建立可证明的安全边界：版本基线、行为测试、数据备份、检查点、特性开关、灰度、监控和回滚。达到这些条件后，再按小提交逐步收敛任务模型、执行管线、持久化和安全控制面。任何阶段出现数据一致性、权限边界或恢复能力不明确的情况，都应停止扩量，保留证据，并回到最后一个可验证的稳定状态。
