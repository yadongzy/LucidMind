# LucidMind 工程深度提升实施方案 v1.0

> 基于 v1.7.1 代码审计 + OpenClaw 对标分析
> 日期: 2026-02-26
> 核心方向: Safety by Default · Progressive Disclosure · Diagnostics Everywhere

---

## 一、三大设计原则定义

### 原则 1: Safety by Default（安全即默认）

**定义**: 系统的每一个入口点（API、CLI、内部调用）都有**自动生效**的安全验证，不依赖调用者手动加验证。安全是基础设施，不是可选功能。

**工程标准**:
- 每个 API 端点必须有 Pydantic 请求模型（不接受 raw dict）
- 每个文件路径参数必须经过路径安全验证（防穿越）
- 每个工具执行必须经过 ToolSafetyGuard 审批链
- 每个插件安装前必须通过安全扫描且扫描结果持久化
- 每个外部输入（用户消息、插件名、MCP 参数）必须有边界检查

### 原则 2: Progressive Disclosure（渐进式披露）

**定义**: 系统加载和呈现信息时，按**需要**分层加载，而非一次性全量加载。减少启动开销、内存占用和信息噪声。

**工程标准**:
- 插件加载三层: metadata（manifest.json 轻量）→ SKILL.md（能力描述）→ resources（代码/依赖/完整加载）
- Brain 工具注入: 按场景分组，不是每次调用都传 108 个工具定义
- 诊断信息: 默认摘要级，按需展开详情级
- 记忆检索: 先粗筛（关键词），再精排（语义相似度）

### 原则 3: Diagnostics Everywhere（诊断无处不在）

**定义**: 系统中每个有意义的操作都产生**结构化诊断记录**（不是 print/logger.info 的非结构化日志），可以被聚合、查询、展示。

**工程标准**:
- 每个操作产生 `DiagnosticEvent`（类型、级别、耗时、输入摘要、输出摘要、错误）
- 诊断事件存储到 `data/diagnostics.jsonl`（追加写，按天轮转）
- API 端点 `GET /api/diagnostics` 可查询最近 N 条
- 前端可查看操作时间线（类似 Chrome DevTools Performance）

## 二、实施阶段与节点

### Phase 0: 安全修复（紧急）— 预计 2 小时

> **目标**: 消除已知安全漏洞，不引入新功能

#### 节点 0.1: ToolSafetyGuard 审批链闭环

**当前问题**:
```
api/main.py L389-392: _safety_guard 已创建，已注入 ws_channel
composite.py L56-62: execute() 未调用 _safety_guard.check()
brain_resilience.py L116: tools.execute(tool_name, params, session_id=session_id) — 传了 session_id
```

**修改方案**:
- `CompositeToolAdapter` 新增 `set_safety_guard(guard)` 方法
- `execute()` 在路由到具体 adapter 前调用 `guard.check(session_id, tool_name, params)`
- `api/main.py` 启动时调用 `tool_adapter.set_safety_guard(_safety_guard)`

**修改文件**:
1. `adapters/tools/composite.py` — 增加 safety guard 集成
2. `api/main.py` — 注入 safety guard 到 tool_adapter

**完成标准**:
- [ ] `execute()` 内部调用 `guard.check()` 在 adapter 路由之前
- [ ] `check()` 返回 `{"approved": False}` 时，`execute()` 返回拒绝结果而非执行
- [ ] 无 WebSocket 连接时仍按 guard 逻辑自动放行（Daemon 场景）

**测试标准**:
- [ ] 单元测试: `test_composite_safety_guard_blocks_dangerous`
- [ ] 单元测试: `test_composite_safety_guard_allows_safe`

**当前问题**:

#### 节点 0.3: API 端点 HTTP 错误码规范化

**当前问题**: 约 40% 的 API 端点在错误时返回 HTTP 200 + `{"error": "..."}` body

- 关键端点新增 Pydantic 请求模型替代 raw `dict`

**修改文件**:
1. `api/plugins.py` — 6 个端点全部规范化
2. `api/mcp.py` — 6 个端点全部规范化

**完成标准**:
- [ ] 所有 error 响应使用 HTTPException（不再 return dict with error key）
- [ ] `POST /api/plugins/hub/install` 使用 Pydantic 模型: `class InstallRequest(BaseModel): name: str`
- [ ] `POST /api/mcp/servers` 使用 Pydantic 模型: `class AddServerRequest(BaseModel): name: str; transport: str; ...`
- [ ] 不存在的资源返回 404，输入错误返回 400

**测试标准**:
- [ ] E2E: GET `/api/plugins/nonexistent` → 404
- [ ] E2E: POST `/api/plugins/hub/install` body `{}` → 422 (Pydantic validation error)
- [ ] E2E: DELETE `/api/mcp/servers/nonexistent` → 404
- [ ] 现有前端代码兼容性验证（不会因 400 响应而崩溃）

### Phase 1: 插件系统三层加载（Progressive Disclosure）— 预计 1 天

> **目标**: 重构插件发现和加载为三层架构，降低启动开销，提升可扩展性

#### 节点 1.1: 插件元数据层（Layer 1: Metadata）

**当前问题**: `discover_skills()` 一次性加载所有插件的完整代码，即使某些插件从未被调用

**设计**:
```
Layer 1 (启动时): 只读 manifest.json → 注册到 _registry
  信息: name, version, description, tools(名称列表), platform, enabled, dependencies
  不加载: Python 代码、Adapter 实例
  目的: 快速启动、API 列表展示、依赖检查
```

**新增文件**:
1. `skills/loader.py` — 三层加载器

**新增数据结构**:
```python
class PluginMeta:
    """Layer 1: 轻量元数据（只从 manifest.json 提取）"""
    name: str
    version: str
    description: str
    tool_names: list[str]     # 工具名列表（不是工具定义）
    platform: list[str]
    enabled: bool
    dependencies: list[str]
    path: Path
    status: str               # "registered" | "loaded" | "active" | "error"
    load_level: int           # 1=metadata, 2=skill_doc, 3=full
```

**完成标准**:
- [ ] 启动时只执行 Layer 1 加载（<100ms 目标）
- [ ] `GET /api/plugins` 可列出所有插件元数据（无需加载代码）
- [ ] 插件状态从 `status: loaded` 细化为 `registered → loaded → active → error`

**测试标准**:
- [ ] 基准测试: 50 个 mock 插件目录，Layer 1 加载时间 < 200ms
- [ ] 单元测试: manifest 缺字段时优雅降级
- [ ] 单元测试: platform 不匹配的插件标记为 `platform_skip` 但仍在 registry

#### 节点 1.2: 技能描述层（Layer 2: SKILL.md）

**当前缺失**: LucidMind 没有 SKILL.md 概念

**设计**:
```
Layer 2 (按需): 读取 SKILL.md → 提供给 Brain 作为工具使用说明
  信息: 使用示例、注意事项、能力边界、配合建议
  触发: Brain 首次需要某个工具的详细说明时
  目的: 让 Brain 更准确地使用工具，减少 system prompt 膨胀
```

**新增规范**:
- `skills/*/SKILL.md` — 可选文件，Markdown 格式
- 最多 2000 字符（超出自动截断）
- Brain 在工具调用失败时自动加载 SKILL.md 到 context

**完成标准**:
- [ ] SKILL.md 规范文档化到 `docs/plugin-guide.md`
- [ ] `PluginMeta` 增加 `skill_doc: str | None` 字段
- [ ] `brain.py` 工具调用失败时自动检查 SKILL.md 并注入 context
- [ ] 至少 3 个内置插件有 SKILL.md（shell, web_search, file）

**测试标准**:
- [ ] 单元测试: 有 SKILL.md 的插件在 Layer 2 加载后 `skill_doc` 非空
- [ ] 单元测试: 没有 SKILL.md 的插件正常工作（向后兼容）
- [ ] 集成测试: Brain 工具调用失败 → 自动加载 SKILL.md → 重试成功率提升

#### 节点 1.3: 完整加载层（Layer 3: Resources）

**设计**:
```
Layer 3 (首次调用时): 加载 Python 代码 → 实例化 Adapter → 注册到 CompositeToolAdapter
  触发: LLM 返回的 tool_call 引用了某个尚未加载的工具
  目的: 按需加载，减少内存占用
```

**修改方案**:
- `CompositeToolAdapter.execute()` 增加懒加载逻辑
- 工具未在 `_tool_map` 中时，检查 `_registry` 中是否有未加载的匹配插件
- 是 → 触发 Layer 3 加载 → 注册 → 执行
- 否 → 触发 `_on_tool_not_found` 搜索安装流程

**完成标准**:
- [ ] 启动时不加载任何插件 Python 代码（全部 Layer 1）
- [ ] 首次工具调用触发按需加载（用户无感）
- [ ] 加载失败产生 DiagnosticEvent 且插件标记为 `error`
- [ ] 热加载 `POST /api/plugins/reload` 仍然可用（全量重扫描）

**测试标准**:
- [ ] 单元测试: 启动后 `_tool_map` 只含内置工具，不含插件工具
- [ ] 集成测试: 调用插件工具 → 触发加载 → 返回正确结果
- [ ] 集成测试: 加载失败的插件不影响其他插件
- [ ] 性能测试: 启动时间对比（当前 vs 三层加载）

### Phase 2: 安全体系化 (Safety by Default 深化) — 预计 1.5 天

> **目标**: 从"有安全功能"升级到"安全架构"

#### 节点 2.1: 插件发现安全加固

**对标 OpenClaw `discovery.ts` 的安全检查**:

**新增检查项**:
1. **路径安全**: `plugin_dir.resolve()` 必须在 `_SKILLS_DIR.resolve()` 内（防 symlink 逃逸）
2. **权限检查**: 插件目录/文件不应是 world-writable（`o+w`），macOS/Linux 下检查
3. **所有权检查**: 插件文件所有者应该是当前用户或 root（防止其他用户植入恶意插件）
4. **Symlink 拒绝**: manifest.json 和 main.py 不应是符号链接
5. **文件大小限制**: 单个 .py 文件 > 500KB 时警告（可能是混淆恶意代码）

**新增文件**:
1. `skills/discovery_safety.py` — 发现阶段安全检查

**新增函数**:
```python
def check_plugin_safety(plugin_dir: Path) -> DiagnosticEvent:
    """
    返回:
        DiagnosticEvent(
            safe=True/False,
            checks=[
                {"name": "path_escape", "passed": True},
                {"name": "world_writable", "passed": True},
                {"name": "symlink", "passed": True},
                {"name": "file_size", "passed": True},
                {"name": "ownership", "passed": True},
            ],
            blocked_reason="..." or None
        )
    """
```

**完成标准**:
- [ ] `discover_skills()` 在加载每个插件前调用 `check_plugin_safety()`
- [ ] 任何检查失败时，插件标记为 `security_blocked`，不加载
- [ ] 安全检查结果存入 `_registry[name]["security"]`
- [ ] `GET /api/plugins` 返回每个插件的安全检查结果

**测试标准**:
- [ ] 单元测试: 创建 world-writable 目录 → 被拒绝
- [ ] 单元测试: 创建 symlink 指向外部文件 → 被拒绝
- [ ] 单元测试: 正常插件目录 → 全部通过
- [ ] 单元测试: 500KB+ 的 .py 文件 → 警告但不阻断

#### 节点 2.2: 安全扫描增强

**对标 OpenClaw `skill-scanner.ts` 缺失能力**:

**新增扫描能力**:
1. **递归扫描**: 当前只扫描 `*.py` 单层，改为递归扫描所有 `.py/.js/.sh/.bat` 文件
2. **文件大小限制**: 单文件 > 1MB 跳过扫描并标记警告
3. **Context-aware 规则**: 某些模式在特定上下文中是安全的（如 `subprocess.run` 在注释中）
4. **扫描结果持久化**: 每次扫描结果写入 `data/scan_history.jsonl`
5. **安全扫描 API**: `POST /api/security/scan/{plugin_name}` — 手动触发对已安装插件的扫描

**修改文件**:
1. `skills/skill_scanner.py` — 增强扫描能力
2. `api/security.py` — 新增扫描端点

**新增模式**:
```python
# 新增 CRITICAL 模式
{"name": "base64_exec", "level": "critical",
 "regex": r"base64\.(b64)?decode.*?(exec|eval|subprocess)",
 "description": "Base64 解码后执行代码（常见混淆手法）"},
{"name": "webhook_exfil", "level": "critical",
 "regex": r"(discord\.com/api/webhooks|hooks\.slack\.com)",
 "description": "向 Discord/Slack Webhook 发送数据"},

# 新增 WARNING 模式
{"name": "global_var_write", "level": "warning",
 "regex": r"globals\(\)\[|setattr\(.*?__builtins__",
 "description": "修改全局变量或内建函数"},
{"name": "temp_file_exec", "level": "warning",
 "regex": r"tempfile\..*(write|open).*?(exec|subprocess|os\.system)",
 "description": "写入临时文件后执行"},
```

**完成标准**:
- [ ] 递归扫描（含 `**/*.py` 不仅是 `*.py`）
- [ ] 文件大小保护（>1MB 跳过 + 警告）
- [ ] 注释行跳过（已有，确认覆盖 `#` 和 `"""` 多行注释）
- [ ] 扫描历史可查（`GET /api/security/scan-history`）
- [ ] 手动扫描端点工作

**测试标准**:
- [ ] 单元测试: 子目录下的 .py 文件能被扫描到
- [ ] 单元测试: 1MB+ 文件被跳过且有警告
- [ ] 单元测试: 新增的 4 个模式各有匹配测试用例
- [ ] 集成测试: `POST /api/security/scan/clipboard` → 返回扫描结果

#### 节点 2.3: MCP Server 安全验证

**当前问题**: `add_server` API 接受任意 command/url，无安全验证

**新增检查**:
1. **Command 白名单**: stdio 模式下，`command` 必须是已知安全命令（`npx`, `node`, `bun`, `python`, `uvx`）或完整路径且存在
2. **URL 验证**: http 模式下，`url` 必须是有效 HTTP(S) URL，禁止 `file://`, `ftp://`
3. **Args 安全**: 拒绝包含 shell 元字符（`|`, `&&`, `;`, `` ` ``）的 args
4. **环境变量过滤**: `env` 字段不允许覆盖 PATH, HOME 等关键变量

**修改文件**:
1. `adapters/tools/mcp_client.py` — 增加 `_validate_server_config()` 方法
2. `api/mcp.py` — 在 `add_server` 中调用验证

**完成标准**:
- [ ] `_validate_server_config()` 返回 `(valid: bool, reason: str)`
- [ ] 不安全的配置返回 400 错误（不静默接受）
- [ ] 现有的 3 个 MCP Server 配置通过验证（向后兼容）

**测试标准**:
- [ ] 单元测试: `command: "rm"` → 拒绝
- [ ] 单元测试: `command: "npx"` → 接受
- [ ] 单元测试: `url: "file:///etc/passwd"` → 拒绝
- [ ] 单元测试: `args: ["-y", "pkg; rm -rf /"]` → 拒绝

### Phase 3: 诊断系统 (Diagnostics Everywhere) — 预计 1 天

> **目标**: 建立统一的结构化诊断体系

#### 节点 3.1: DiagnosticEvent 核心数据结构

**新增文件**: `diagnostics.py`

**数据结构**:
```python
@dataclass
class DiagnosticEvent:
    """结构化诊断事件 — 系统中每个有意义操作的记录。"""
    timestamp: float          # Unix timestamp
    category: str             # "tool_call" | "plugin_load" | "mcp_request" | "security_check" | "brain_process" | "api_request"
    action: str               # "execute" | "install" | "scan" | "discover" | ...
    status: str               # "success" | "failure" | "blocked" | "timeout" | "skipped"
    duration_ms: float        # 耗时（毫秒）
    input_summary: str        # 输入摘要（≤200字符）
    output_summary: str       # 输出摘要（≤200字符）
    error: str | None         # 错误信息
    metadata: dict            # 额外键值对（session_id, tool_name, plugin_name 等）
    level: str                # "debug" | "info" | "warning" | "error"

class DiagnosticCollector:
    """诊断事件收集器 — 单例，全局使用。"""

    def record(self, event: DiagnosticEvent) -> None:
        """记录事件到内存 + 持久化到 JSONL 文件。"""

    def query(self, category: str = None, status: str = None,
              since: float = None, limit: int = 50) -> list[DiagnosticEvent]:
        """查询诊断事件。"""

    def summary(self, since: float = None) -> dict:
        """生成诊断摘要（各类别的成功率、平均耗时等）。"""
```

**完成标准**:
- [ ] `DiagnosticEvent` 数据类定义完整
- [ ] `DiagnosticCollector` 单例可全局访问（`from diagnostics import get_collector`）
- [ ] JSONL 持久化到 `data/diagnostics.jsonl`（追加写）
- [ ] 文件自动轮转: 每天一个文件 `diagnostics_2026-02-26.jsonl`
- [ ] 内存缓存最近 1000 条，文件无上限

**测试标准**:
- [ ] 单元测试: 记录事件 → 查询事件 → 数据一致
- [ ] 单元测试: 文件轮转逻辑正确（跨天新建文件）
- [ ] 单元测试: `summary()` 正确计算成功率和平均耗时
- [ ] 性能测试: 10000 条记录/秒不阻塞主线程

**在以下位置增加诊断记录**:

| 位置 | 类别 | 记录内容 |
|------|------|---------|
| `composite.py execute()` | `tool_call` | 工具名、参数摘要、耗时、成功/失败 |
| `mcp_client.py execute()` | `mcp_request` | 服务器名、工具名、耗时、成功/失败/重连 |

| `skill_scanner.py scan_file()` | `security_check` | 文件名、发现数量、各级别数 |

## 八、ACE 论文分析与 Phase 8 实施方案

> **论文**: Agentic Context Engineering: Evolving Contexts for Self-Improving Language Models
> **来源**: arXiv:2510.04618v2 | ICLR 2026
> **作者**: Qizheng Zhang, Changran Hu 等 (SambaNova + Stanford)
> **GitHub**: https://github.com/sambanova/ACE

### 8.1 ACE 核心思想

ACE 将 Context 视为**持续演化的 Playbook**——不是压缩式摘要，而是结构化的策略条目集合，通过三角色分工持续积累和精炼。

**三角色架构**:
```
Generator (执行者) → 生成推理轨迹、执行工具调用
     ↓
Reflector (反思者) → 从成功/失败中提炼具体策略和教训
     ↓
Curator (整合者)  → 用非 LLM 确定性逻辑将 delta 合并入 Playbook
```

**两大创新**:
1. **Incremental Delta Updates**: Context = 结构化 bullet 集合，每条有 ID + helpful/harmful 计数器。更新是局部 delta，非全量重写。
2. **Grow-and-Refine**: 新条目追加，旧条目原地更新计数器，定期语义去重。防止 context collapse。

**关键结果**:
- AppWorld: **+17.1%**（无标注），DeepSeek-V3.1 匹敌 GPT-4.1 级 IBM CUGA
- 金融推理: **+8.6%** 平均提升
- 适配延迟: **降低 86.9%**（增量 delta vs 全量重写）
- Token 成本: **降低 83.6%**

### 8.2 与 LucidMind 的映射

| ACE 概念 | LucidMind 对应 | 差距 |
|----------|---------------|------|
| Generator | brain.py process() + 工具执行 | ✅ 已有 |
| Reflector | brain_learning._detect_learning_signal (部分) | 🔧 混合了反思+整合 |
| Curator | brain_learning._add_lesson (部分) | 🔧 无确定性合并 |
| Bullet (结构化条目) | lessons.json 条目 → MemoryStore | 🔧 缺 helpful/harmful 计数 |
| Delta Update | ❌ 缺失 | 当前 append-only |
| Grow-and-Refine | ❌ 缺失 | 无计数器/去重/合并 |
| Context as Playbook | SOUL.md + lessons | ✅ 雏形 |
| Offline Adaptation | ❌ 缺失 | 无离线预热 |
| Online Adaptation | brain_learning 实时学习 | ✅ 已有 |
| Collapse 防护 | ❌ 缺失 | _smart_compact_history 有类似风险 |
