## 架构升级: OpenClaw + SAS 混合模式 — 2026-02-27 17:30

### 背景
深度分析 OpenClaw 任务队列机制与 Scheduler-Agent-Supervisor (SAS) 模式后，
采用混合最优解：OpenClaw 的执行引擎 + SAS 的 Supervisor 智慧 + 轻量任务分解器。

### 新建文件

| 文件 | 行数 | 说明 |
|------|------|------|
| `command_queue.py` | ~280 | Lane-based 异步命令队列（对标 OpenClaw command-queue.ts） |
| `task_decomposer.py` | ~150 | 轻量任务分解器（混合模式的 Scheduler 角色） |
| `tests/test_command_queue.py` | ~400 | 17 个测试覆盖队列全部功能 |

### 修改文件

| 文件 | 改动 | 说明 |
|------|------|------|
| `brain_task_executor.py` | 重构 | while-true 内联重试 + 软失败检测 + 任务分解集成 |
| `brain_daemon.py` | 增强 | 优雅关闭(wait_for_idle) + command_queue 状态集成 |
| `websocket_channel.py` | 增强 | CHAT lane 统一入队 + 即时唤醒 Daemon |
| `task_dispatcher.py` | 新增 | `update_task_progress()` 中间状态推送 |

### 架构要点

**1. 统一命令队列 (command_queue.py)**
- 4 车道: CHAT(max=3) / DAEMON(max=2) / CRON(max=1) / SUBAGENT(max=2)
- Generation 计数器防幽灵任务（重启后旧任务自动忽略）
- Pump 自驱动排水（任务完成后立即驱动下一个）
- Gateway Draining 优雅关闭

**2. 内联重试循环 (brain_task_executor.py)**
- 对标 OpenClaw run.ts 的 while(true) 循环
- 软失败（空承诺+工具未执行）→ 指数退避内联重试 ×3
- 硬失败（异常）→ 外部 fail_task 重试
- 超时 → 内联重试后降级到 fail_task

**3. 轻量任务分解器 (task_decomposer.py)**
- 仅 complex 级别任务触发 LLM 分解（规则预判，省 token）
- 子任务标记 decomposed=True 防递归
- 父子关联：子任务全部完成后自动恢复父任务
- 学习/自检/任务驱动学习不分解

**4. Supervisor 功能确认（已有，无需新增）**
- `fail_task()` + `max_retries` = 重试策略 ✅
- `_handle_task_failure()` → `enqueue_learning()` = 自愈学习 ✅
- `_notify_escalation()` → 上报老师 = 人工升级 ✅
- `SelfCheckEngine` + `RepairEngine` = 健康监控 ✅

**5. 实时状态推送 (task_dispatcher.py)**
- `update_task_progress()` 推送执行中间状态
- 通过 WebSocket `task_progress` 事件实时送达前端

### 测试结果
- `test_command_queue.py`: 25/25 ✅（17 队列 + 1 进度推送 + 2 内联重试 + 5 任务分解）
- 全量回归: **380/380 passed** ✅（含所有历史测试，0 破坏）

## ENH-1~4: 四车道全量集成 + 反馈闭环 + 前端看板增强 — 2026-02-27 17:50

### ENH-1: CRON lane 集成
- **修改文件**: `brain_daemon.py`
- **改动**: `_run_engines()` 不再直接执行后台引擎，而是通过 `CommandLane.CRON` 入队
- **新增方法**: `_run_engines_inner()` 承载原有逻辑
- **效果**: 后台引擎（每日任务/自检/修复/学习）与 DAEMON/CHAT 物理隔离，不互相阻塞
- **降级**: CRON lane 入队失败时自动 fallback 直接执行

### ENH-2: SUBAGENT lane 集成
- **修改文件**: `brain_task_executor.py`
- **改动**: `_execute_task()` 中根据 `task.get("parent_id")` 选择车道
  - 有 `parent_id` → `CommandLane.SUBAGENT`（最大并发2）
  - 无 `parent_id` → `CommandLane.DAEMON`（最大并发2）
- **效果**: 分解后的子任务与父任务物理隔离，子任务不会占用 DAEMON 车道配额

### ENH-3: 任务分解反馈闭环
- **修改文件**: `task_dispatcher.py`
- **改动 1**: `_resume_parent()` 重写 — 检查所有 sibling 子任务状态
  - 全部完成 → 父任务标记 `completed`，`progress` 写入聚合摘要
  - 部分失败 → 父任务标记 `ready`（可重试），摘要含失败详情
  - 全部失败 → 父任务标记 `failed`
  - 有子任务未结束 → 不恢复，继续等待
- **改动 2**: `fail_task()` 中子任务 escalated 后也调用 `_resume_parent()`
- **修复**: 之前子任务失败/上报后父任务永远 blocked 的 bug

### ENH-4: 前端任务看板增强
- **修改文件**:
  - `frontend-v2/src/ui/views/scheduler.js` — 任务队列表头新增"进度"列，行内展示 `↳子任务` 标记 + 实时进度文本
  - `frontend-v2/src/styles/chat.css` — 新增 `.sched-col--progress` 样式
  - `api/main.py` — `_task_notify_hook` 增加 `progress` 和 `parent_id` 字段推送
- **效果**: 任务看板实时展示每个任务的执行进度、子任务关系、聚合结果

### 四车道使用总结
| Lane | 用途 | 最大并发 | 入口 |
|------|------|----------|------|
| CHAT | 用户对话 | 3 | `websocket_channel.py` |
| DAEMON | 普通任务执行 | 2 | `brain_task_executor._execute_task` |
| CRON | 后台引擎（每日/自检/修复/学习） | 1 | `brain_daemon._run_engines` |
| SUBAGENT | 分解后子任务 | 2 | `brain_task_executor._execute_task`（有parent_id） |

### 测试结果
- `test_command_queue.py`: **31/31** ✅（+6 新测试: CRON lane/SUBAGENT lane/父任务聚合/部分失败/notify进度）
- 全量回归: **386/386 passed** ✅（含所有历史测试，0 破坏）

## 🔧 修复 #1: LLM 工具调用 — 2026-02-27 19:38

### 研究分析

#### OpenClaw 关键发现
- **OpenClaw 并不解析 MiniMax XML tool call 来执行它们** — 它只是**剥离**这些 XML 标签用于用户显示
- OpenClaw 的 `stripMinimaxToolCallXml()` (pi-embedded-utils.ts) 仅用于清理文本，不转换为可执行工具调用
- 这说明 OpenClaw 使用的 MiniMax 模型是通过**原生 function calling API** 正常工作的，XML 泄漏只是偶发的显示问题
- OpenClaw 还处理了 Gemini 的 downgraded tool call 文本格式（`[Tool Call: name (ID: ...)]`）

#### MiniMax-M1 在 LucidMind 中的实际行为
- MiniMax-M1 在我们的系统中**完全**以 XML 文本形式输出工具调用
- `response.get("tool_calls")` 始终为空
- 实际 XML 格式：
  ```
  [tool_call]
  <invoke name="web_search">
  <parameter name="query">今天的科技新闻</parameter>
  <parameter name="max_results">8</parameter>
  </invoke>
  ```

#### 网络最佳实践 (Morph Documentation)
- XML tool call 比 JSON 性能更好（避免 constrained decoding 的性能损失）
- Cursor、Cline 等顶级 AI 编辑器都使用 XML tool call 格式
- 解析方案：正则表达式提取 `<tool_name><parameter>value</parameter></tool_name>` 结构

### 实施方案（已完成）

#### 新建文件
- `tool_call_parser.py` — 独立 XML tool call 解析模块
  - `has_xml_tool_calls(text)` — 快速预检
  - `parse_xml_tool_calls(text)` — 解析 XML → 标准 tool_calls 格式
  - `strip_xml_tool_calls(text)` — 剥离 XML 保留纯文本
- `tests/test_tool_call_parser.py` — 26 个测试用例全部通过

#### 修改文件
- `brain.py` — 最小改动（1行import + 5行逻辑）
  - L26: `from tool_call_parser import parse_xml_tool_calls, strip_xml_tool_calls`
  - L180-185: 在 `tool_calls = response.get("tool_calls")` 后，检查文本中的 XML tool call 并转换

### 测试结果 ✅
- **web_search**: 成功调用（网络超时是 proxy/网络问题，工具本身执行正常）
- **mcp_filesystem_list_directory**: 成功列出桌面文件（截图确认）
- **第二次 web_search (小红书热点)**: 成功调用
- 26 个单元测试 + 67 个回归测试全部通过

### ⚠️ 后续待做（记录不立即执行）
- **原生 function calling 方案**: 参考 OpenClaw 的方式，让 MiniMax API 直接返回结构化 tool_calls
  - 需要研究 MiniMax API 的 function calling 参数格式
  - 当前 XML 解析为**临时兼容方案**，长期应走原生 FC
  - OpenClaw 使用 `@mariozechner/pi-ai` SDK 与 MiniMax 交互，其中 function calling 是原生支持的
