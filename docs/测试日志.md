## 第五轮: 架构分析 + 两层修复 — 2026-02-28 19:24

### 第四轮修复验证结果（截图确认）

**改进**: 任务看板只有1个任务（不再是3个） ✅
**仍有问题**:

| # | 问题 | 现象 |
|---|------|------|
| 1 | 任务看板无步骤显示 | 只显示总任务"我有本地摄像头..."，不显示Brain执行的具体步骤（检查Python→检查OpenCV→...） |
| 2 | Brain让用户选择导致任务未完成 | Brain问"你想先安装OpenCV，还是用其他方式拍照？"→ 等待用户选择 → Daemon重试 → 最终仍未拍照 → 任务标记"已完成+承诺未兑现" |
| 3 | 完成标准以中间步骤为准 | Brain给了"方案建议"就算完成，而非"拍照成功"才算完成 |

### 架构分析（Jeff Sutherland / Scrum Definition of Done 视角）

**核心问题**: Brain 把"提供选择"当作任务完成，而非"达成目标"当作完成。

**决策分级原则**:

| 决策类型 | 当前行为 | 应有行为 |
|---------|---------|---------|
| 技术选型（A/B方案） | ❌ 问用户选 | Brain自主选最优方案执行 |
| 安装软件 | ❌ 问用户确认 | Brain自主安装（已有安全审批层兜底） |
| 涉及安全/隐私/花费 | ✅ 问用户确认 | 正确 |
| 不确定用户意图 | ✅ 问用户澄清 | 正确 |

**应有流程**:
```
用户目标 → Brain拆分步骤 → 自主选择最优路径 → 逐步执行+实时更新进度
     ↓                              ↓
任务看板显示步骤              仅安全/隐私决策才问用户
     ↓
所有步骤完成 = 目标完成
```

### 两层修复方案

**Layer 1: Prompt层（低成本、高影响）**
- 修改系统提示加入"自主决策原则"
- Brain遇到技术选型时自主判断最优方案，不问用户
- 仅涉及安全/隐私/不可逆操作时才请求用户确认

**Layer 2: 代码层（中等成本）**
- 任务进度结构化: Brain每完成一个工具调用 → 更新步骤进度
- 前端任务看板展示步骤列表（可展开子项）
- 完成标准: 以最终目标为准，"给了方案建议"不等于"完成"

### 第四轮代码修复回顾

**一个对话目标 = 一个任务**（已实现）:

| 机制 | 说明 |
|------|------|
| `_session_tasks: dict[str, str]` | 类级别映射 session_id → task_id，跨消息复用同一任务 |
| 任务复用 | 后续消息自动复用现有活跃任务，更新进度而非创建新任务 |
| 提问检测 `_detect_reply_question()` | 回复以 `?`/`？`/`需要我` 结尾 → 任务保持 running |
| 多步追踪 | 工具执行完一步但非新任务 → 更新进度"步骤完成"，继续 running |

**完成判断逻辑**:
```
if 承诺结尾/空回复:        → fail_task + 唤醒Daemon
elif 回复以提问结尾:       → 保持running（等待用户响应）
elif 工具已执行且非首次消息: → 步骤完成，继续running
else:                     → 目标完成 ✅
```
- 单元测试: 256/256 passed ✅
- 人工验证: ⚠️ 任务合并成1个✅，但仍有上述3个问题

## 第二轮测试 + BUG修复: 任务看板3个问题 — 2026-02-28 18:26

### 测试发现（截图确认）

| # | 问题 | 现象 |
|---|------|------|
| 1 | 执行中看板无任务 | 工具已在调用，任务看板显示"暂无任务" |
| 2 | 完成后才出现且立即已完成 | 第一阶段结束后任务才出现在看板，且状态直接是"已完成" |
| 3 | 伪承诺再次出现 | "让我检查Python环境：" — 对话中断，未继续执行 |

### 根因（全在 `websocket_channel.py` `_safe_process()`）

旧逻辑：
```python
result = await brain.process(...)   # 先执行
task = td.enqueue(...)              # 执行完才创建任务
td.complete_task(task["id"])         # 创建后立即标记完成，无质量检查
```

- **问题1**: 任务在 `brain.process()` 返回后才创建 → 执行期间看板为空
- **问题2**: 创建后立即 `complete_task()` → 无论结果如何都标记完成
- **问题3**: 对话流直走 `brain.process()`，不经过 `brain_task_executor` 的软失败检测

### 修复（⚠️ 未经人工验证）

新逻辑：
```python
task = td.enqueue(...)              # 1. 执行前创建任务（running状态）
td.update_task_progress(task_id, "执行中")
result = await brain.process(...)   # 2. 执行
# 3. 执行后质量检查：
#    - 空回复 → fail_task
#    - 承诺结尾 → fail_task + 唤醒Daemon重试
#    - 正常完成 → complete_task
```

| 改动 | 文件 | 说明 |
|------|------|------|
| 任务提前创建 | `websocket_channel.py` L254-267 | `brain.process()` 前创建 running 态任务 |
| 质量检查 | `websocket_channel.py` L273-305 | 空回复/承诺结尾 → `fail_task` + `_wake_daemon` |
| 承诺模式 | `websocket_channel.py` L233-240 | 复用 `_PROMISE_TAIL_PATTERNS` 列表 |

- 单元测试: 256/256 passed ✅

## 架构升级: OpenClaw + SAS 混合模式 — 2026-02-27 17:30

### 背景
深度分析 OpenClaw 任务队列机制与 Scheduler-Agent-Supervisor (SAS) 模式后，

### 架构要点

**1. 统一命令队列 (command_queue.py)**
- 4 车道: CHAT(max=3) / DAEMON(max=2) / CRON(max=1) / SUBAGENT(max=2)
- Generation 计数器防幽灵任务（重启后旧任务自动忽略）
- Pump 自驱动排水（任务完成后立即驱动下一个）
- Gateway Draining 优雅关闭

**2. 内联重试循环 (brain_task_executor.py)**
- 对标 OpenClaw run.ts 的 while(true) 循环
- 软失败（空承诺+工具未执行）→ 指数退避内联重试 ×3
- 硬失败（异常）→ 外部 fail_task 重试
- 超时 → 内联重试后降级到 fail_task

**3. 轻量任务分解器 (task_decomposer.py)**
- 仅 complex 级别任务触发 LLM 分解（规则预判，省 token）
- 子任务标记 decomposed=True 防递归
- 父子关联：子任务全部完成后自动恢复父任务
- 学习/自检/任务驱动学习不分解

**4. Supervisor 功能确认（已有，无需新增）**
- `fail_task()` + `max_retries` = 重试策略 ✅
- `_handle_task_failure()` → `enqueue_learning()` = 自愈学习 ✅
- `_notify_escalation()` → 上报老师 = 人工升级 ✅
- `SelfCheckEngine` + `RepairEngine` = 健康监控 ✅

**5. 实时状态推送 (task_dispatcher.py)**
- `update_task_progress()` 推送执行中间状态
- 通过 WebSocket `task_progress` 事件实时送达前端

## 🔧 修复 #1: LLM 工具调用 — 2026-02-27 19:38

### 研究分析

#### OpenClaw 关键发现
- **OpenClaw 并不解析 MiniMax XML tool call 来执行它们** — 它只是**剥离**这些 XML 标签用于用户显示
- OpenClaw 的 `stripMinimaxToolCallXml()` (pi-embedded-utils.ts) 仅用于清理文本，不转换为可执行工具调用
- 这说明 OpenClaw 使用的 MiniMax 模型是通过**原生 function calling API** 正常工作的，XML 泄漏只是偶发的显示问题
- OpenClaw 还处理了 Gemini 的 downgraded tool call 文本格式（`[Tool Call: name (ID: ...)]`）

#### MiniMax-M1 在 LucidMind 中的实际行为
- MiniMax-M1 在我们的系统中**完全**以 XML 文本形式输出工具调用
- `response.get("tool_calls")` 始终为空
- 实际 XML 格式：
  ```
  [tool_call]
  <invoke name="web_search">
  <parameter name="query">今天的科技新闻</parameter>
  <parameter name="max_results">8</parameter>
  </invoke>
  ```

#### 网络最佳实践 (Morph Documentation)
- XML tool call 比 JSON 性能更好（避免 constrained decoding 的性能损失）
- Cursor、Cline 等顶级 AI 编辑器都使用 XML tool call 格式
- 解析方案：正则表达式提取 `<tool_name><parameter>value</parameter></tool_name>` 结构

### 实施方案（已完成）

#### 新建文件
- `tool_call_parser.py` — 独立 XML tool call 解析模块
  - `has_xml_tool_calls(text)` — 快速预检
  - `parse_xml_tool_calls(text)` — 解析 XML → 标准 tool_calls 格式
  - `strip_xml_tool_calls(text)` — 剥离 XML 保留纯文本
- `tests/test_tool_call_parser.py` — 26 个测试用例全部通过

#### 修改文件
- `brain.py` — 最小改动（1行import + 5行逻辑）
  - L26: `from tool_call_parser import parse_xml_tool_calls, strip_xml_tool_calls`
  - L180-185: 在 `tool_calls = response.get("tool_calls")` 后，检查文本中的 XML tool call 并转换

### 测试结果 ✅
- **web_search**: 成功调用（网络超时是 proxy/网络问题，工具本身执行正常）
- **mcp_filesystem_list_directory**: 成功列出桌面文件（截图确认）
- **第二次 web_search (小红书热点)**: 成功调用
- 26 个单元测试 + 67 个回归测试全部通过

### ⚠️ 后续待做（记录不立即执行）

  - 需要研究 MiniMax API 的 function calling 参数格式

## 任务编排深度分析与最优方案 — 2026-02-28

### 问题根因
用户发现任务执行存在4个严重问题：
1. 任务完成质量差（Brain问用户选择而非自主执行）
2. 状态不同步（对话显示完成但队列仍running）
3. 无实时步骤动态
4. Daemon抢占Chat任务导致重复执行

根本原因：**扁平状态机（pending→running→completed）试图建模需要层次化状态机才能正确表达的系统**。Chat和Daemon两条路径并发操作同一任务状态，没有互斥和所有权机制。

### 研究范围
1. **OpenClaw对标项目** — 深度阅读 run.ts(1165行)、attempt.ts(1362行)、command-queue.ts、hooks/types.ts
2. **学术论文** — arXiv:2512.12791 Beyond Task Completion 评估框架
3. **最佳实践** — Planner-Executor框架(EmergentMind综述)、LangGraph状态机模式、Harel Statecharts理论

### OpenClaw vs LucidMind 对比

| 维度 | OpenClaw | LucidMind |
|------|---------|-----------|
| 对话处理 | 直连SDK prompt()，无任务队列 | 经task_dispatcher入队 |
| 工具循环 | SDK内置黑盒(prompt→tool_use→tool_result→end_turn) | brain.py手写while循环 |
| 完成判断 | SDK自动(stop_reason=end_turn) | 手写正则is_question/is_promise |
| 实时事件 | subscription事件流实时推送 | 仅process()返回后更新 |
| 任务面板 | 无 | 有（但状态不准） |
| 后台任务 | 无 | 有Daemon+Cron |

**结论**：OpenClaw方案不适合直接照搬（缺任务面板和后台任务），但"对话不进队列"的核心思路必须学习。

### 选定方案：方案D — 双层分离 + 轻量Goal Tracker

**专家依据**：David Harel（Statecharts发明人）的层次化状态机理论

**核心设计**：
```
Goal Tracker（只读状态记录器，不排队不调度不执行）
    ├── Chat路径: 直连brain.process()，实时回调步骤→Goal Tracker
    └── Daemon路径: 仍通过task_dispatcher，只管后台任务
```

**改动清单**：
1. `goal_tracker.py`（新建~60行）— 轻量目标追踪器，记录goal_id/steps/status
2. `websocket_channel.py` — Chat路径不再创建task_dispatcher任务，直连brain.process()
3. `brain.py` — 工具循环中实时回调步骤事件给Goal Tracker
4. `brain_daemon.py` — Daemon跳过source="chat"的任务
5. `prompts/tool_usage.md` — 增加[GOAL_COMPLETE]标记让LLM自主判断完成

**优势**：Chat零延迟、无并发竞争（Goal Tracker只读）、完成判断由启发式规则+LLM行为信号。

### 方案D实施记录 — 2026-02-28 20:15

**已完成改动**：
1. `goal_tracker.py`（新建，120行）— 轻量目标追踪器，WebSocket实时广播
2. `websocket_channel.py` — Chat路径用goal_tracker替代task_dispatcher，软失败仍入队td作安全网
3. `brain.py` — 工具循环中新增 `emit("tool_step", tool_name)` 实时推送
4. `api/main.py` — 启动时注入 `goal_tracker.set_ws_channel()`
5. `prompts/tool_usage.md` — 增加目标完成原则（禁止承诺性结尾、禁止追问）

**测试回归**：全量通过（0 failures）

**架构变化**：
- Chat消息不再创建task_dispatcher任务 → Daemon不会抢占对话任务
- Goal Tracker是只读记录器，不排队不调度 → 无并发竞争
- 工具步骤通过WebSocket `tool_step`事件实时推送 → 前端可实时渲染
- 软失败（空承诺/空回复）仍入队task_dispatcher(source="chat_retry") → Daemon安全网保留

## 2026-02-28 技能仓库架构深度对比分析（LucidMind vs OpenClaw）

**分析专家视角**：Mitchell Hashimoto（HashiCorp创始人，Terraform/Vault/go-plugin插件架构设计者）

### 核心发现

#### 1. 根本哲学差异
- **LucidMind**: 技能 = 可执行代码（manifest.json + main.py，Adapter类提供list_tools/execute）

- **LucidMind**: `skills/__init__.py`(423行)承担过多职责（发现/注册/热加载/Hub/安全/MCP），存在God Module反模式
- **OpenClaw**: 17+个文件职责清晰分离（workspace.ts/config.ts/refresh.ts/frontmatter.ts等），模块化领先一个级别

#### 3. 安全模型
- **LucidMind 更深**（4层）: skill_scanner → discovery_safety → trust_level(audited/sandboxed) → tool_safety(SENSITIVE确认)
- **OpenClaw 更智能**（2层但规则有上下文感知requiresContext）

#### 4. 自愈能力
- **LucidMind 独有**: brain_resilience.py → 工具未找到 → 搜索PluginHub → 安装 → LLM自动创建 → 热加载重试（杀手级特性）
- **OpenClaw 没有**此闭环

- **LucidMind**: 无显式token预算管理（15个技能暂不痛）
- **OpenClaw**: maxSkillsInPrompt=150, maxSkillsPromptChars=30000, 二分查找最优子集

#### 6. 热加载
- **LucidMind**: 手动API触发，清除模块缓存
- **OpenClaw**: chokidar文件监听 + debounce自动重载，体验更好

#### 7. MCP集成
- **LucidMind 独有**: 每个技能自动生成MCP Server脚本（mcp_wrapper.py），任何MCP客户端可调用
- **OpenClaw**: 技能是文档不是工具，不需要MCP封装

### 结论

> OpenClaw是更成熟的工程系统（模块化、类型安全、Token管理），LucidMind是更有野心的AI系统（自愈、自创、进程隔离）。LucidMind应在保持AI-native优势的同时，补齐工程规范性。

### LucidMind应改进
1. 拆分`skills/__init__.py` God Module → registry.py/hub.py/discovery.py/reload.py
2. 增加Token预算管理（技能超20个时必须有上限）
3. 文件监听自动重载（watchdog替代手动API）
4. loader.py三层加载要真正落地（discover_skills仍全量加载）

### LucidMind应保持的优势
1. 技能=可执行代码（确定性执行比提示更可靠）
2. 自愈闭环（_on_tool_not_found → 搜索 → 安装/LLM创建 → 重试）
3. 进程隔离安全模型（sandboxed trust level）
4. MCP自动封装（远期竞争力）

## 2026-02-28 第二轮深度分析：是否有更完美方案 + 分水岭方向选择

**分析专家视角**：Joe Armstrong（1950–2019，Erlang创造者，容错隔离系统架构之父）

### 选择Joe Armstrong的理由
1. Erlang/OTP是人类历史上唯一将「进程隔离+热代码替换+监督树容错」从语言层面内建的系统，达到九个9可用性

- **原则2**：技能可以是code/prompt/hybrid三种形态
- **原则3**：Let it crash + 监督树（崩溃自动重启，故障精确隔离）
- **原则4**：能力即消息类型（tool/prompt/script统一为capability声明）
