## 一、背景与问题

### 1.1 当前系统现状

LucidMind 已有一套诊断-修复闭环：

```
SelfCheckEngine.daily_check()  →  发现问题  →  report_issue()
                                                    │
RepairEngine.repair_all()  ←  get_open_issues()  ←──┘
       │
       ├─ _auto_fix_minor()   → 轻微修复
       ├─ _fix_medium()       → 中等修复
       ├─ _fix_severe()       → 严重修复
       └─ _fix_fatal()        → 致命问题
```

### 1.2 审计发现的问题

| # | 问题 | 严重度 | 文件 |
|---|------|--------|------|
| 1 | RepairEngine 去重逻辑指向 JSON 文件，系统已切到 SQLite | 致命 | repair_engine.py:63-73 |
| 2 | `_auto_fix_minor` 默认 `return True` 假阳性 | 严重 | repair_engine.py:76 |
| 3 | issue_tracker 无 max_retry 限制，导致 2476 次无效重试 | 严重 | issue_tracker.py:36-43 |
| 4 | `_fix_severe/_fix_fatal` 只打日志不修复 | 中等 | repair_engine.py:95-110 |
| 5 | Brain 已有 read_file/write_file/run_script/git_* 工具但从未用于自修复 | 架构缺陷 | — |

### 1.3 行业基准数据

| 来源 | 数据 |
|------|------|
| RepairAgent (ICSE 2025) | Defects4J 19.6% 自主修复率, $0.14/bug |
| SWE-bench Verified (2026) | 最强 Agent ≈ 62-65% 解决率 |
| SWE-bench Pro | 工业级 ≈ 43-46% |
| C3 AI Alchemist | 需沙箱 + CI/CD guardrails |

### 2.2 修复层级与判定逻辑

```python
# 伪代码
async def smart_repair(issue):
    severity = issue["severity"]
    retries = issue["retries"]
    
    # L1: 数据层直接修复
    if severity == "minor" and retries < 3:
        return await self._data_layer_fix(issue)
    
    # L2: Brain 自服务修复
    if severity in ("minor", "medium") and retries < 10:
        return await self._brain_self_repair(issue)
    
    # L3: 外部代理修复
    if retries >= 10 or severity in ("severe", "fatal"):
        return await self._delegate_to_external(issue)
    
    # 超限: 自动关闭 + 通知用户
    if retries >= 20:
        close_issue(issue["id"], "auto_closed_max_retry")
        notify_user(f"问题无法自动修复: {issue['desc']}")
```

### 2.3 核心文件保护名单

以下文件 Brain **绝对不能修改**（修改可能导致系统崩溃）：

```python
_PROTECTED_FILES = [
    "brain.py",           # 核心推理循环
    "brain_daemon.py",    # 后台守护进程
    "brain_config.py",    # 配置
    "api/main.py",        # API 入口
    "api/startup.py",     # 启动流程
    "command_queue.py",   # 并发控制
    "ports/",             # 所有端口接口
]
```

### 2.4 Brain 自修复任务模板

```
你是 LucidMind 的自修复子系统。请按以下步骤修复问题：

问题描述: {issue_desc}
问题文件: {file_path}
问题行号: {line_range}

步骤：
1. 使用 read_file 读取问题文件
2. 分析问题根因
3. 使用 git_status 确认工作区干净
4. 使用 write_file 写入修复
5. 使用 run_script 执行: cd /path/to/project && python3 -m pytest tests/ -x -q
6. 如果测试通过 → 使用 git_commit 提交
7. 如果测试失败 → 使用 run_script 执行: cd /path/to/project && git checkout -- {file_path}

安全规则：
- 不得修改 _PROTECTED_FILES 中的文件
- 每次只修改一个文件
- 修改前必须先读取完整文件
- 修改后必须运行测试验证
```

## 三、联动设计

### 3.1 与经验库联动

```
修复成功 → _record_repair_lesson() → 记录到经验库
                                        │
下次类似问题 → get_lessons("修复") → 查找历史修复经验
                                        │
                                   优先尝试已验证的修复方法
```

### 3.2 与记忆文件联动

- 创建 `REPAIR_PATTERNS.md` evergreen 记忆文件
- 记录成功的修复模式（文件→问题→修复方法→验证结果）
- Brain 修复前先检索记忆文件

### 3.3 与学习引擎联动

- `LearningEngine.maybe_learn()` 分析 repair 失败的 issue
- 提取失败模式 → 生成"教训"经验
- 灵魂引擎可固化频繁出现的修复模式为规则

### 3.4 与 MCP 联动（外部代理）

```json
// data/mcp_servers.json 新增配置
{

```

### 3.5 与前端联动

- 诊断页增加"修复状态"列：open → repairing → verifying → closed
- 增加"手动触发修复"按钮
- 增加"委托外部修复"按钮
- 修复进度实时推送到 WebSocket

## 五、风险评估

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| Brain 修改代码导致系统崩溃 | 中 | 致命 | _PROTECTED_FILES + git 回滚 + pytest 验证 |
| LLM 生成错误修复 | 高 | 中 | 测试必须通过 + 只改一个文件 |
| 无限修复循环 | 中 | 低 | max_retry=20 自动关闭 |
| 外部 Agent 返回不兼容 patch | 中 | 中 | patch 格式验证 + 测试 |
| 修复引入新 bug | 中 | 高 | git branch 隔离 + 全量测试 |
