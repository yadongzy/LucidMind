# LucidMind 项目目标与可落地执行方案

> 日期: 2026-05-06  
> 范围: LucidMind 与 Codex、OpenClaw、Hermes Agent、群体智能体操作系统竞品、Reversa 的综合分析  
> 目标: 把竞品分析收束成可执行产品路线，而不是继续堆概念

---

## 1. 最终定位

LucidMind 不应定位为 Codex 的替代品，也不应复制 OpenClaw 的通道数量，或正面硬拼 Hermes 的运行后端生态。

更稳的定位是：

> **LucidMind 是一个有长期记忆、可视化治理和插件闭环的个人/项目 AI 大脑。**
> 它负责理解用户、记住项目、维护状态、调度工具；代码任务可以交给 Codex、Claude Code、Gemini CLI 或本地工具执行。

换句话说：

| 项目 | 最强定位 | LucidMind 的关系 |
|---|---|---|
| Codex | 专业软件工程执行层 | 下游高质量 coding executor |
| OpenClaw | 多通道个人 AI Gateway | 学安全、通道、插件边界，不追通道数量 |
| Hermes Agent | 自进化个人 agent + 多后端执行 | 学身份连续性、技能闭环、运行后端，不照抄 |
| 群体智能体 OS 竞品 | 长期工程内核 + 群体协作 | 战略同类，需用更小闭环抢先落地 |
| Reversa | 代码反向工程为可执行规格 | 可借鉴规格化流水线、置信度、checkpoint |

LucidMind 的一句话产品目标：

> **用户给一个目标，LucidMind 读取项目和个人上下文，形成计划，调度合适执行器完成任务，验证结果，生成报告，并把关键决策写入长期记忆。**

## 2. 核心用户场景

### 2.1 项目长期协作者

用户希望 AI 不只是一次性回答，而是长期参与项目。

典型流程：

1. 用户说：“继续昨天那个 MCP 配置问题。”
2. LucidMind 检索项目记忆、任务状态、历史决策、未解决问题。
3. LucidMind 给出当前项目状态摘要。
4. LucidMind 生成下一步计划。
5. 如需代码修改，调度 Codex 或本地工具执行。
6. 跑测试、读取日志、检查服务状态。
7. 生成任务报告。
8. 把“做了什么、为什么这样做、遗留风险、下一步”写入项目记忆。

### 2.2 可治理的本地 Agent OS

用户希望 AI 能动手，但不能失控。

关键要求：

- 所有危险工具默认需要审批。
- 没有前端连接时，危险操作不能自动放行。
- 每个任务必须有状态、日志、产物和回滚建议。
- 自动生成或安装的 skill 必须先进入隔离区，不能立刻拥有高权限。
- 用户可以在 Web UI 看到记忆、任务、工具、模型、MCP、审批记录。

### 2.3 项目规格与知识萃取

用户希望 AI 先理解项目，再修改项目。

LucidMind 应支持一个轻量 Reversa-like 流程：

1. Scout: 扫描项目结构、语言、依赖、入口、测试、模块。
2. Archaeologist: 深读核心模块，提取函数、数据结构、控制流。
3. Detective: 提取业务规则、状态机、权限、隐含约束。
4. Writer: 生成项目规格、架构图、任务地图。
5. Reviewer: 检查规格一致性，提出需要用户确认的问题。

该流程不应替代 Reversa，而是把 Reversa 的思想内化为 LucidMind 的“项目理解模式”。

## 3. 产品原则

### 3.1 不做什么

LucidMind 暂时不做：

- 不追 OpenClaw 的 20+ 通道数量。
- 不重造 Codex 的专业代码执行能力。
- 不一开始做复杂的 agent hierarchy 或 manager-of-managers。
- 不把所有实验性工具都包装成稳定能力。
- 不允许 LLM 自动创建的 skill 直接获得写文件、shell、网络等高权限。

### 3.2 必须做什么

LucidMind 必须做：

- 长期记忆 source of truth 明确化。
- 项目状态可查询。
- 任务闭环可复现。
- 工具权限可审计。
- 规格和报告有置信度标注。
- 失败时给出真实状态，而不是“我会去做”。
- 复杂任务优先产出计划和检查点，而不是直接乱改。

### 3.3 设计口径

默认用户不是想看概念，而是想知道：

- 当前项目处于什么状态？
- 你准备做什么？
- 你做了什么？
- 结果验证了吗？
- 风险在哪里？
- 下次能接着做吗？

因此所有核心功能都应围绕“状态、闭环、验证、记忆、报告”组织。

## 4. 目标架构

### 4.1 三层架构

```
┌──────────────────────────────────────────────┐
│              Experience Layer                │
│  Web UI / Chat / Telegram / Feishu / CLI     │
│  记忆视图 · 任务视图 · 审批 · 报告 · 配置       │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│              LucidMind Brain Layer            │
│  Intent · Context · Memory · Plan · Govern    │
│  Task State · Skill Routing · Executor Router │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│              Execution Layer                  │
│  Built-in Tools · Python Skills · MCP Servers │
│  Codex/Claude/Gemini Executors · Browser      │
│  Docker/SSH Sandbox                           │
└──────────────────────────────────────────────┘
```

### 4.2 三核双循环

借鉴竞品“群体智能体操作系统”的表达，但落到可实现模块：

三核：

1. **Memory Core**: 记住用户、项目、决策、任务、经验。
2. **Execution Core**: 调度工具、MCP、Codex、本地 shell、浏览器。
3. **Governance Core**: 审批、边界、状态、回滚、报告、验证。

双循环：

1. **任务闭环**: 目标 → 计划 → 执行 → 验证 → 报告。
2. **学习闭环**: 结果 → 复盘 → 记忆 → 规则/skill 更新 → 下次注入。

### 4.3 九个 Slot

Slot 是扩展点，不是先做大而全的抽象。每个 Slot 必须有最小可用实现。

| Slot | 作用 | 最小实现 |
|---|---|---|
| Identity Slot | 用户/人格/项目身份 | USER.md、SOUL.md、project profile |
| Memory Slot | 长期记忆 | Markdown source + SQLite/FTS/vector index |
| Context Slot | 当前上下文 | 项目状态、历史摘要、任务状态 |
| Tool Slot | 工具能力 | CompositeToolAdapter + tool registry |
| Skill Slot | 插件能力 | Python skill manifest + lazy load |
| MCP Slot | 外部工具生态 | MCP client + health status |
| Executor Slot | 专业执行器 | Codex/Claude/Gemini adapter，先 CLI 适配 |
| Governance Slot | 安全治理 | approval、policy、audit log、quarantine |
| Report Slot | 结果沉淀 | task report、confidence markers、memory writeback |

## 5. MVP: 一个必须打穿的杀手闭环

### 5.1 MVP 名称

**Project Continuity Loop**

### 5.2 MVP 用户故事

用户在 LucidMind 中打开一个项目，然后说：

> “分析这个项目，找出最值得做的下一步，并完成一个小修复。”

LucidMind 必须能够：

1. 扫描项目。
2. 生成项目状态摘要。
3. 识别一个低风险改进点。
4. 生成计划。
5. 请求用户批准。
6. 执行修改。
7. 运行测试或静态检查。
8. 生成报告。
9. 写入项目记忆。
10. 下次用户问“上次做到哪”，能准确回答。

### 5.3 MVP 验收标准

必须满足：

- 项目状态摘要中包含语言、入口、测试命令、核心模块、风险。
- 每个任务有唯一 task_id。
- 每个任务有状态流转: `planned -> approved -> running -> verifying -> done/failed`。
- 每次文件修改前有计划，修改后有 diff 摘要。
- 至少运行一个验证命令。
- 报告写入 `data/project_reports/<project>/<task_id>.md`。
- 关键决策写入 `data/memory/projects/<project>.md`。
- 用户下次询问时能检索到报告和决策。

## 6. 阶段计划

## Phase 0: 产品边界冻结与真实性标注

周期: 2-3 天

目标:

把现有能力分成 stable、beta、experimental、degraded，避免 README 和 UI 暗示所有功能都可靠。

任务:

1. 新增 `docs/CAPABILITY_MATRIX.md`。
2. 为核心能力标注状态:
   - Brain 对话: stable
   - 工具调用: beta
   - Memory Flush: beta
   - Markdown Memory: beta
   - MCP: beta
   - 自动 skill 创建: experimental
   - 自修复: experimental
   - 多通道: beta/experimental 分别标注
3. API `/api/status` 增加 degraded 信息。
4. 前端 Diagnostics 展示能力状态。

验收:

- 用户能看到哪些能力稳定、哪些降级。
- 向量不可用时明确显示“FTS fallback”。
- MCP server 断开时明确显示。

## Phase 1: 安全治理加固

周期: 1 周

目标:

把 LucidMind 从“能动手”变成“能被信任地动手”。

任务:

1. 修改 ToolSafetyGuard 默认策略:
   - dangerous 超时默认拒绝。
   - 无 WebSocket 连接时 dangerous 默认拒绝。
   - sensitive 可配置为超时拒绝或只读放行。
2. 增加 policy 文件:
   - `data/security/policy.json`
   - 工具级别: safe/sensitive/dangerous/blocked
   - 路径级别: workspace/tmp/blocked
3. 自动生成 skill quarantine:
   - 新 skill 初始状态为 quarantined。
   - 只允许 list/read/self-test。
   - 用户批准后才 active。
4. 审批记录落盘:
   - `data/audit/tool_approvals.jsonl`
   - 包含 session_id、tool、params 摘要、decision、time。
5. 前端增加审批历史和工具白名单管理。

验收:

- 危险工具在无 UI 连接时不会自动执行。
- 自动创建 skill 不能直接运行 shell/write_file。
- 审批记录可查询。
- 测试覆盖 dangerous/sensitive/safe/quarantine 四类。

---

## Phase 2: 统一记忆系统

周期: 1-2 周

目标:

明确 Markdown 是 source of truth，SQLite/FTS/vector 是索引层。

任务:

1. 统一目录:
   - `data/memory/MEMORY.md`: 常青记忆
   - `data/memory/daily/YYYY-MM-DD.md`: 每日记忆
   - `data/memory/projects/<project>.md`: 项目记忆
   - `data/memory/users/<user>.md`: 用户记忆
2. MemoryStore 增加 source metadata:
   - `source_type`: markdown/session/lesson/profile/tool
   - `source_path`
   - `source_hash`
3. Markdown index 支持删除同步:
   - 文件删除后索引也删除或标记 stale。
4. Memory Flush 改为写项目/每日两份:
   - 对话摘要写 daily。
   - 项目决策写 project memory。
5. 搜索结果展示来源:
   - UI 中显示来自哪个文件、置信度、更新时间。

验收:

- 用户直接编辑 Markdown 后，30 秒内可被检索。
- 删除 Markdown 段落后，不再检索出旧内容。
- 项目记忆和个人记忆能分开检索。
- 压缩历史后仍能问回旧决策。

## Phase 3: 项目状态索引

周期: 1 周

目标:

让 LucidMind 能回答“这个项目现在是什么状态”。

任务:

1. 新增 Project Scanner:
   - 语言和框架识别。
   - 入口文件。
   - 测试命令。
   - 构建命令。
   - 关键目录。
   - 最近 git diff。
   - dirty worktree 状态。
2. 新增项目状态文件:
   - `data/projects/<project_id>/state.json`
   - `data/projects/<project_id>/surface.json`
3. 借鉴 Reversa Scout:
   - 生成 `inventory.md`
   - 生成 `dependencies.md`
   - 生成 `surface.json`
4. 前端增加 Project 页面:
   - 项目摘要。
   - 最近任务。
   - 最近报告。
   - 风险和 gap。

验收:

- 对 LucidMind 自身运行 scanner 后，能识别 Python + FastAPI + Vite。
- 能列出主要模块: brain、memory、skills、api、frontend。
- 能识别测试命令和启动命令。
- 能显示 dirty worktree，且不误改用户变更。

## Phase 4: 任务闭环与报告

周期: 1-2 周

目标:

所有复杂任务都变成可跟踪、可验证、可复盘的闭环。

任务:

1. 定义 Task State Machine:
   - `draft`
   - `planned`
   - `approved`
   - `running`
   - `blocked`
   - `verifying`
   - `done`
   - `failed`
2. 每个任务生成 plan:
   - 目标。
   - 范围。
   - 风险。
   - 文件候选。
   - 验证命令。
   - 回滚策略。
3. 执行后生成 report:
   - 做了什么。
   - 改了哪些文件。
   - 验证结果。
   - 遗留风险。
   - 下次建议。
4. 报告置信度标注:
   - 🟢 CONFIRMED: 命令/文件/测试直接证明。
   - 🟡 INFERRED: 根据代码推断。
   - 🔴 GAP: 需要用户确认。
5. 报告写回记忆。

验收:

- 任一复杂任务完成后都能在 UI 看到 report。
- 用户问“刚才做了什么”时，从 report 回答。
- 失败任务保留失败原因和下一步建议。

## Phase 5: Codex/外部执行器集成

周期: 1 周

目标:

LucidMind 不重造 Codex，而是把 Codex 作为工程执行器。

任务:

1. 定义 ExecutorPort:
   - `can_handle(task)`
   - `run(task, context)`
   - `status(run_id)`
   - `collect_artifacts(run_id)`
2. 实现 Codex CLI adapter:
   - 先支持生成 prompt 和调用命令。
   - 后续支持读取结果、diff、测试输出。
3. Executor Router:
   - coding task → Codex/Claude/Gemini。
   - local automation → Python tools/MCP。
   - browser task → browser tool。
4. 任务报告合并:
   - Codex 输出归档到 LucidMind report。
   - 关键决策写入项目记忆。

验收:

- 用户可以让 LucidMind 把代码任务交给 Codex。
- Codex 执行结果被 LucidMind 汇总、验证、记忆。
- LucidMind 不直接覆盖 Codex 的工作区安全策略。

验收:

## 7. Reversa 对 LucidMind 的帮助

### 7.1 Reversa 是什么

Reversa 是一个 Node CLI/agent skill 框架，目标是：

> 把遗留系统反向工程成可执行、可追踪、可供 AI agent 使用的规格。

它不是运行时 AI 助手，也不是多通道 agent。它更像“代码知识萃取流水线”。

核心结构:

- `npx reversa install` 安装 agent skills。
- 支持 Claude Code、Codex、Cursor、Gemini CLI 等 13 类引擎。
- 只写 `.reversa/` 和 `_reversa_sdd/`，不修改原项目文件。
- 通过 5 阶段 pipeline 生成规格。
- 使用 `.reversa/state.json` 做 checkpoint/resume。
- 每个结论使用 🟢/🟡/🔴 置信度标注。

### 7.2 对 LucidMind 最有价值的点

#### A. 规格化流水线

Reversa 的 Scout → Archaeologist → Detective → Writer → Reviewer 很适合被 LucidMind 吸收。

对应 LucidMind:

| Reversa | LucidMind 可吸收能力 |
|---|---|
| Scout | 项目状态扫描 |
| Archaeologist | 核心模块深读 |
| Detective | 隐含规则/状态机/权限提取 |
| Writer | 项目规格和任务计划生成 |
| Reviewer | gap、风险、置信度检查 |

这能解决 LucidMind 当前“先行动，后理解”的风险。

#### B. Checkpoint/resume

Reversa 的 `.reversa/state.json` 机制非常适合 LucidMind 的长任务。

LucidMind 可以引入:

- `data/tasks/<task_id>/state.json`
- `phase`
- `completed`
- `pending`
- `checkpoints`
- `created_files`
- `artifacts`

这样长任务中断后可以继续，不必完全依赖聊天历史。

#### C. 只写输出目录的安全边界

Reversa 的绝对规则是只写 `.reversa/` 和 `_reversa_sdd/`。这点对 LucidMind 很重要。

LucidMind 可以把“分析模式”和“执行模式”分开：

- 分析模式: 只能写 `data/projects/<project>/analysis/`。
- 执行模式: 需要用户批准后才可写项目源码。

#### D. 置信度标注

Reversa 的 🟢/🟡/🔴 是一个很好的产品机制。

LucidMind 应将它用于:

- 项目规格。
- 任务报告。
- 记忆条目。
- 诊断结论。
- 自动学习经验。

尤其是记忆系统：不要所有记忆都当事实，应区分 confirmed/inferred/user_confirmed。

#### E. 增量分析与验证

Reversa 本地已有 `diff-analyzer.js`、`spec-validator.js`、`cost-estimator.js` 这些模块。实现不复杂，但方向正确。

LucidMind 可借鉴:

- git diff → affected modules。
- spec 必需产物检查。
- Mermaid 检查。
- 文件引用存在性检查。
- gap 比例告警。
- token/成本预估。

### 7.3 不建议直接复用的点

不建议直接把 Reversa 代码搬进 LucidMind:

- Reversa 是 Node CLI，LucidMind 是 Python/FastAPI。
- Reversa 的 agent skill 是葡语为主，需重写为中文/英文产品口径。
- Reversa 的执行依赖外部 coding agent，不是 LucidMind 内核。
- Reversa 当前本地工作树有未提交修改，不适合直接 vendor。

建议方式:

1. 借鉴流程和数据模型。
2. 用 Python 重写最小实现。
3. 将 Reversa 作为可选外部工具或参考模板。
4. 后续可以做 `reversa_import`，读取 `_reversa_sdd/` 产物进入 LucidMind project memory。

### 7.4 Reversa 可直接启发的 LucidMind 新功能

功能名: **Project Spec Mode**

入口:

- Web UI: Project → Analyze
- Chat: “分析这个项目并生成规格”
- CLI: `lucidmind project analyze`

输出:

```
data/projects/<project_id>/specs/
├── inventory.md
├── dependencies.md
├── code-analysis.md
├── domain.md
├── architecture.md
├── questions.md
```

核心价值:

- 让 LucidMind 修改项目前先拥有 operational contracts。
- 让 Codex 等执行器获得更好的上下文。
- 让项目记忆从“聊天摘要”升级成“可验证规格”。

## 8. 实施顺序建议

最推荐顺序:

1. Phase 1 安全治理。
2. Phase 2 统一记忆。
3. Phase 3 项目状态索引。
4. Phase 4 任务闭环报告。
5. Phase 5 Codex 执行器。
6. Phase 6 Reversa-like 项目理解模式。
7. Phase 7 Web 产品化。

原因:

- 没有安全治理，执行器越强越危险。
- 没有统一记忆，长期连续性会混乱。
- 没有项目状态，任务闭环没有地基。
- 没有报告，学习闭环没有可靠输入。
- 没有执行器，LucidMind 会陷入自己写代码能力不足。
- 没有项目理解模式，长期会继续靠聊天上下文硬撑。

## 10. 成功标准

三个月内，LucidMind 应该能稳定演示这个场景：

> 用户打开 LucidMind，选择一个项目，说“继续上次的计划”。  
> LucidMind 展示项目状态、历史决策、未完成任务，提出下一步。  
> 用户批准后，LucidMind 调用合适执行器完成修改，运行验证，生成报告。  
> 下次用户回来，LucidMind 能准确说清楚上次做了什么、为什么做、还有什么风险。

如果这个闭环成立，LucidMind 就不需要声称自己“超过 Codex”。它会在 Codex 不负责的长期认知层、治理层、项目记忆层建立自己的价值。
